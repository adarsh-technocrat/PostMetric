title: "POST Payment"
description: "Record a payment using API key authentication"
---

Record payments and link them to visitors for revenue attribution.

## Endpoint

```
POST /api/v1/payment
```

## Authentication

Requires API key authentication.

## Request body

| Field               | Type    | Required | Description                                                          |
| ------------------- | ------- | -------- | -------------------------------------------------------------------- |
| `providerPaymentId` | string  | Yes      | Unique payment id. Re-sending the same id is safe. Alias: `transaction_id` |
| `amount`            | number  | Yes      | Amount in major units (e.g. 99.99). `0` for a free trial             |
| `provider`          | string  | No       | `stripe`, `lemonsqueezy`, `polar`, `paddle` or `other` (default)     |
| `currency`          | string  | No       | ISO code, defaults to `USD`                                          |
| `visitorId`         | string  | No       | From the `_pm_vid` cookie. Aliases: `postmetric_visitor_id`, `datafast_visitor_id` |
| `sessionId`         | string  | No       | From the `_pm_sid` cookie                                            |
| `customerEmail`     | string  | No       | Aliases: `customer_email`, `email`                                   |
| `customerId`        | string  | No       | Your billing system's customer id. Alias: `customer_id`              |
| `renewal`           | boolean | No       | Marks a recurring renewal                                            |
| `refunded`          | boolean | No       | Marks a refund                                                       |
| `timestamp`         | string  | No       | ISO 8601 time of the payment, defaults to now                        |
| `metadata`          | object  | No       | Anything else to store                                               |

Without `visitorId`, the payment is attributed through the customer's earlier payments or a reported email, the same way synced payments are.

## Request example

```bash
curl -X POST "https://your-domain.com/api/v1/payment" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "stripe",
    "providerPaymentId": "pi_1234567890",
    "amount": 99.99,
    "currency": "USD",
    "customerEmail": "customer@example.com",
    "visitorId": "visitor_123",
    "sessionId": "session_456",
    "metadata": {
      "orderId": "order_789"
    }
  }'
```

## Response

### Success response (200)

```json
{
  "status": "success",
  "data": {
    "paymentId": "payment_abc123",
    "message": "Payment recorded successfully"
  }
}
```

### Error responses

#### Missing required fields (400)

```json
{
  "status": "error",
  "error": {
    "code": 400,
    "message": "provider, providerPaymentId, and amount are required"
  }
}
```

#### Unauthorized (401)

```json
{
  "status": "error",
  "error": {
    "code": 401,
    "message": "Unauthorized. Invalid or missing API key."
  }
}
```

## Linking payments to visitors

Payments are automatically linked to visitors using:

1. **Visitor/Session IDs** (most reliable) - Include `visitorId` and `sessionId` in the request
2. **Email matching** - If user identification is enabled, payments are linked via `customerEmail`
3. **Timestamp correlation** - Fallback method using payment timestamp

## Use cases

- **Custom payment providers** - Record payments from providers not supported by webhooks
- **Manual payment entry** - Record payments manually
- **Payment reconciliation** - Sync payments from external systems
- **Testing** - Test revenue attribution
